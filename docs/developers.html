02The signal

A pothole lasts milliseconds. Its signal lasts long enough to be understood.

Road anomalies make recognisable patterns in motion. The SDK samples linear acceleration and gravity at about 50 Hz and projects one onto the other, so it reads the force perpendicular to the road however the phone is mounted.

  1. Baseline gravity · 9.81 m/s²
  2. Drop wheel falls in · 6–7 m/s²
  3. Impact far edge, suspension compresses · 14–18 m/s²
  4. Recovery back to baseline
Dip
6–7 m/s²The wheel drops into the hole
Spike
14–18 m/s²It strikes the far edge

≈ 50 HzLinear acceleration and gravity
Event duration
150–400 msFrom first drop to recovery

Class A

Pothole

Dip, then spike. The wheel drops into the depression before striking the far edge.

Class B

Speed bump

Spike, then dip. A raised surface makes the reverse sequence, which is how the two are told apart.

Class C

Rough patch

Repeated irregular movement. No single dominant impact, but variance stays high across the whole window.

03How it works

From a jolt in a cupholder to a point on a map.

Five steps turn an ordinary phone movement into a structured road-quality event.

On the phoneNetworkOn your server
  1. 01

    Sense

    Read the road through your phone.

    Accelerometer, gravity and gyroscope at about 50 Hz, with GPS. Nothing runs below 15 km/h.

    50 Hz · GPS 1 Hz
  2. 02

    Detect

    Recognise the impact.

    Each reading is compared with a rolling baseline, and the gyroscope has to confirm real motion, which filters out ordinary driving.

    4.0 m/s² · car threshold
  3. 03

    Buffer

    Keep the signal on the device.

    Events are written to SQLite on the phone before anything touches the network.

    SQLite · offline first
  4. 04

    Upload

    Send only what matters.

    WorkManager sends batches when there is a connection and retries with exponential backoff.

    POST /v1/ingest/batch
  5. 05

    Cluster

    Turn single events into road intelligence.

    The Go backend stores events in SQLite or PostgreSQL and groups nearby reports into clusters, scored by how much they agree.

    DBSCAN · 30 m · every 5 min

04Principles

Built for real phones on real roads.

Six decisions shape the SDK and the backend. Each one is a trade-off made on purpose.

P/01Privacy first

Only the bump leaves the phone.

Asphalt does not need to know where you are going. It captures the road anomaly, not your journey. Raw sensor streams, device identifiers and route histories are never uploaded.

  • No user accounts
  • No continuous tracking
  • No device IDs
  • Location only at an event

P/02Battery aware

15km/h

Intelligence without constant sensing.

Sensor processing is gated by vehicle speed. Uploads are batched to avoid waking the radio.

P/03Orientation independent

Any mount. One consistent signal.

Flat, upright or in a cupholder, readings are projected onto the gravity vector, so orientation does not change detection.

P/04Vehicle aware

The same road. Different physical responses.

A car and a motorcycle feel the same pothole differently, so each has its own threshold and weight.

VehicleThresholdWeight
Carfour_wheeler4.0 m/s²1.0×
Motorcycletwo_wheeler5.0 m/s²0.8×

Motorcycles also get turn suppression and a wider baseline window.

P/05Collective confidence

One report is a rumour. Several are a pattern.

A single detection could be anything. A cluster needs at least two events within 30 m, and confidence rises as more vehicles, and more kinds of vehicle, independently report the same place.

P/06Offline first & modular

Built to work independently.

Events wait in local SQLite until there is a connection. The SDK, backend and contracts are independent: point the SDK at your own server, or send the backend events from sources other than Android.

06Get started

One line in your app. One command for the backend.

Start with the Android SDK. Run the backend locally. Connect your app to a road intelligence pipeline.

AAndroid SDK

Kotlin · Android 7.0+

AndroidManifest.xml · Activity.kt
<!-- AndroidManifest.xml, inside <application> -->
<meta-data android:name="io.asphalt.INGEST_URL"
    android:value="https://your-host/v1/ingest/batch" />

// when a trip starts: asks for location, then runs
Asphalt.requestPermissionAndStart(this)

Reads the ingest URL from the manifest, asks for location, then starts detecting.

BBackend

Go · Docker

Terminal
cd backend
docker build -t asphalt .
docker run -p 8080:8080 -v asphalt:/data asphalt
# API on :8080, data in built-in SQLite

curl http://localhost:8080/v1/health

Set DATABASE_URL to a postgres:// address to use PostgreSQL instead.

07Known limitations

Built with transparency. Still evolving.

Road conditions are complex. Asphalt v1 makes deliberate trade-offs, and knowing them is part of building road intelligence people can rely on.

  1. L/01

    No per-device calibration

    Detection thresholds are set by vehicle type, not tuned to each phone.

    v1 · open
  2. L/02

    Quiet roads stay uncertain

    Roads with few passing vehicles keep low confidence until more reports arrive.

    v1 · open
  3. L/03

    GPS spoofing is limited, not prevented

    Multi-report scoring reduces the impact of false submissions, but does not stop them.

    v1 · open
  4. L/04

    Tall buildings blur location

    GPS can drift 30–50 m between towers, wider than the 30 m cluster radius.

    v1 · open
