01 · The signal

A pothole lasts 150 to 400 milliseconds. That is enough.

The SDK samples linear acceleration and gravity at about 50 Hz and projects one onto the other, so it reads the force normal to the road however the phone is mounted. A pothole shows up as a dip and then a spike.

Pothole

Dip, then spike. The wheel drops in, then strikes the far edge.

Speed bump

Spike, then dip. The same shape in reverse order is how the two are told apart.

Rough patch

No dominant peak. Variance stays high across the whole window.

02 · How it works

From a jolt in a cupholder to a point on a map.

  1. 01

    Sense

    Accelerometer, gravity and gyroscope at about 50 Hz. Nothing runs below 15 km/h.

    TYPE_LINEAR_ACCELERATION
    TYPE_GRAVITY · GPS 1 Hz
  2. 02

    Detect

    The spike-dip detector compares each reading to a rolling baseline. The gyroscope has to confirm real motion.

    threshold 4.0 m/s² (car)
  3. 03

    Buffer

    Events are written to SQLite on the phone before anything touches the network.

    offline first
  4. 04

    Upload

    WorkManager sends batches when there is signal and retries with exponential backoff.

    POST /v1/ingest/batch
  5. 05

    Cluster

    The Go backend stores events in PostGIS and groups nearby reports into scored clusters.

    DBSCAN · 30 m · every 5 min

03 · Principles

Built for real phones on real roads.

Privacy first

Only the bump leaves the phone.

No raw sensor data, no account, no device identifier, no route. Location is attached to an anomaly event and nothing else. This is a whole event:

{
  "anomaly_type": "pothole",
  "intensity": 0.65,
  "speed_kmh": 38.6,
  "vehicle_type": "four_wheeler",
  "latitude": 40.6796,
  "longitude": -73.9531,
  "accuracy_m": 8.0
}
  • No user accounts
  • No continuous tracking
  • No device IDs

Battery aware

15km/h

Sensors stay off below the speed gate. Uploads are batched to avoid waking the radio.

Any mount

Flat, upright or in a cupholder.

Readings are projected onto the gravity vector, so orientation does not change detection.

Vehicle profiles

A car and a motorcycle feel the same pothole differently.

VehicleThresholdWeight
Car · four_wheeler4.0 m/s²1.0×
Motorcycle · two_wheeler5.0 m/s²0.8×

Motorcycles also get turn suppression and a wider baseline window.

Confidence

One report is a rumour. Several are a pothole.

A cluster needs at least two events within 30 m. Agreement from more reports and more vehicle types raises confidence, and old reports decay over 90 days.

2 car reports0.58
3 car reports0.60
+ another vehicle type+0.08

Offline first

No signal, no problem.

Events wait in local SQLite until there is a connection.

Modular

Use the parts you need.

The SDK, backend and contracts are independent. Point the SDK at your own server, or send the backend events from sources other than Android. The event schema, batch format and HTTP API are published as JSON Schema and OpenAPI 3.1.

05 · Get started

Two calls in your app. One command for the backend.

AAdd the Android SDK

// Application.onCreate()
Asphalt.init(this, AsphaltConfig(
    ingestUrl = "https://your-host/v1/ingest/batch",
    vehicleType = VehicleType.FOUR_WHEELER
))

// after location permission is granted
Asphalt.start()

BRun the backend

cd backend
docker compose up --build
# API on http://localhost:8080

curl http://localhost:8080/v1/health

06 · Known limitations

What v1 does not do yet.

  • No per-device calibrationThresholds are set per vehicle type, not tuned to each phone.
  • Quiet roads stay uncertainRoads with few drivers keep low confidence until more reports arrive.
  • GPS spoofing is limited, not preventedMulti-report scoring reduces its impact.
  • Tall buildings blur locationGPS can drift 30–50 m between towers, wider than the 30 m cluster radius.
