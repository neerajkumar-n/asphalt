Architecture

From the phone to the map, end to end.

Two parts you can run on their own: an Android SDK that detects anomalies on the phone, and a Go server that turns many reports into a scored map. This page follows one pothole through both.

      03What leaves the phone
      
      
      This is the whole event. Nothing else is sent.
      
      
      Each field is there for a reason the server can use. Anything that could follow a person from trip to trip stays on the device or is never collected.
      
    
      
    
      
      
      
        
      
          
      FieldExampleWhy it is sent
      
          
            
      event_id7c3e6b2a…Random per event, so a retried upload is not counted twice.
      
            
      timestamp_ms1793892600000Recency in the confidence score; stale reports fade over 90 days.

      04Run it your way
      
      
      Start with one command. Grow when you need to.
      
    
      
    
      
      
      
        
      
          
          
          
        
      
        
      
          
      
            
      SQLite, built in
      
            
      The default. One container, one data file, nothing else to install. Right for a city pilot, a fleet, or trying it out.
      
            
        
              
      • Database · a file at /data/asphalt.db
        • 
              
      • Scale · one server instance
        • 
              
      • Backups · copy the volume
        • 
            
      
          
      
          
      cd backend
docker build -t asphalt .
docker run -p 8080:8080 -v asphalt:/data asphalt

# point the SDK at
http://your-host:8080/v1/ingest/batch
      
        
      
        
      
          
      
            
      PostgreSQL 13 or newer
      
            
      For several server instances behind a load balancer, or a managed database. No extensions needed; the same schema runs on both.
      
            
        
              
      • Database · any PostgreSQL, including managed ones
        • 
              
      • Scale · add server replicas; the server keeps no state
        • 
              
      • Reads · map endpoints can use a read replica
        • 
            
      
          
      
          
      # everything locally
cd backend
docker compose up --build

# or any server, any PostgreSQL
DATABASE_URL=postgres://user:pass@host/asphalt \
  ./asphalt-server
      
        
      
        
      
          
      
            
      Mix and match
      
            
      The SDK, server and contracts are independent. The event and batch formats are published, so either side can be replaced.
      
            
        
              
      • Your own server · accept the batch format at any URL
        • 
              
      • Other sources · send events to the backend from iOS, dashcams or fleet hardware
        • 
              
      • Contracts · JSON Schema for events, OpenAPI 3.1 for the HTTP API
        • 
            
      
          
      
          
      # the contracts
contracts/event.schema.json
contracts/api.yaml
contracts/example-batch.json

# send the example batch
curl -X POST http://localhost:8080/v1/ingest/batch \
  -H "Content-Type: application/json" \
  -d @contracts/example-batch.json
      
        
      
      
      
    
      
  
      

      



      
  
      
    
      
      
      05HTTP API
      
      
      One way in, three ways out.
      
      
      Phones write to one endpoint. Maps and dashboards read from the others. Open an endpoint for an example.
      
    
      
    
      
      
      
        
      
          POST/v1/ingest/batchPhones upload batches of events
          
      
            
        
              
      • ≤ 500 events
      • ≤ 2 MB
      • not over 5 min in the future
      • not over 7 days old
      • same batch_id is a no-op
      • same event_id is ignored
        • 
            
      
            
      Request
      {
  "batch_id": "5f0cd4f7-…",
  "submitted_at_ms": 1793892900000,
  "events": [ /* events, as in 03 */ ]
}
      
            
      Response · 200
      {
  "batch_id": "5f0cd4f7-…",
  "accepted_count": 12,
  "duplicate": false
}

      06Design decisions
      
      
      Why it is built this way.
      
    
      
    
      
      
      
        
      Detection
      On the phone, not the server
      Streaming 50 Hz sensor data would cost battery, data and privacy. Detecting on the device means only a few dozen bytes per bump ever leave it.
      
        
      Clustering
      DBSCAN at 30 m
      Potholes line up along roads, not in neat circles. DBSCAN finds any shape, needs no cluster count, and drops lone reports as noise.
      
        
      Upload
      Batches, not a stream
      Waking the radio is one of the biggest battery costs. WorkManager uploads every 15 minutes at most, sooner when 200 events wait, and retries with backoff.
      
        
      Scoring
      Confidence, not certainty
      Any single report can be wrong. Scoring agreement, recency and vehicle variety lets a map choose its own threshold instead of trusting one phone.
      
        
      Backend
      Go, one static binary
      No runtime to install, a small container, and goroutines that handle many uploads at once with a standard library that covers HTTP, SQL and JSON.
      
        
      Storage
      SQLite first
      The schema uses no extensions and clustering runs in Go, so a single file is enough to start. PostgreSQL is one environment variable away.
